# Khayt review — desktop, website, iOS, cloud (2026-07-28)

A review of all four surfaces. Every claim below was measured or run, not
inferred; where something was flagged and then dismissed, the reason is given,
because a review that only lists suspicions is a review nobody can act on.

**Headline: the codebase is in good health.** The findings below are mostly
"worth doing", not "on fire". Three things are genuinely worth scheduling, and
one is a release blocker only in the sense that the release notes are already
written for it.

## Fix first

### 1. The website states things that are no longer true
**Evidence:** `index.html` claims "3 designs in 3.3" and "8 languages, 9 in
beta". Reality: 9 design shells on disk and all 9 locales shipping.

This is the only surface where a user is told something false. It is a
five-minute edit, and it is already coupled to the 3.4.0 cut.

### 2. `renderer/logs.js:134` is the wrong complexity class — **fixed**
```js
const clientsWithOrders = clients.filter(c => printLog.some(o => o.clientId === c.id));
```
Runs on **every render** of the logs tab. Measured:

| Shop size | Nested (current) | Set-based | Factor |
|---|---|---|---|
| 200 clients × 2k orders | 0.25 ms | 0.21 ms | 1.2× |
| 2,000 × 20k | 15.0 ms | 1.5 ms | 10× |
| 5,000 × 50k | **100.2 ms** | 4.0 ms | 25× |

Now `clientsWithAnyOrder()`, built on a Set. It matters more than first estimated:
`renderLogs()` has **64 call sites**.

Guarded by `test/logs-client-filter.test.js`, which pins the complexity **without
timing anything** — it counts property reads through getters, so a linear pass
touches each record about once and a nested one touches them clients × orders
times. Deterministic, and it fails for the right reason: reverting the fix
reports `got 90300, expected ~1200`.

**Scanned for the same pattern repo-wide: 15 sites, 14 dismissed** — the rest
scan a small inner array (parts per order, colours per row, a bounded selection),
so they are linear in practice.

Also corrected from the first draft: the log table's **rows** are already
paginated (`filtered.slice(0, logDisplayLimit)`), so row rendering was never the
problem.

### 3. The companion has no offline state
**Evidence:** no caching in `KhaytCompanion/Services/` — every screen is fed
live from the LAN API. Out of Wi-Fi range the app shows nothing at all.

For a tool whose entire premise is being used away from the desk, "useless in the
back room with bad signal" is a real product limit. A read-only cache of the last
successful fetch (queue, orders, inventory) would remove it. Writes can keep
requiring a connection — that avoids the whole offline-merge problem.

## Worth scheduling

### 4. Accessibility has never been looked at — but it is in better shape than this review first said
**Correction.** The first version of this document estimated "roughly 52
icon-only buttons" from a crude regex. A proper check — one that strips markup,
HTML entities, emoji and template expressions, and honours `aria-label`,
`data-i18n-aria`, `aria-labelledby` and `title` — found **3 nameless buttons out
of 802**. The original figure was wrong and is corrected here rather than quietly
dropped.

The three were real, and two of them were **delete** controls (a `🗑` on a
waiting-list entry, a `×` on a saved preset) plus the PIN pad's `⌫`. An unnamed
destructive button is the worst case: a screen-reader user cannot tell it from
any other unnamed button until after they press it. All three are now labelled,
and `test/button-accessible-name.test.js` keeps it that way.

What remains genuinely unmeasured is keyboard navigation: Escape/focus handling
appears in 9 files, so modals are not uniformly dismissible. That is the next
thing to look at, and it needs a real pass rather than a static scan.

### 5. Four renderer modules over 400 lines have no test at all
`converter` (1,198), `shell` (1,030), `printfiles` (687), `hueforge` (500).

`shell.js` is the one to care about: it decides which tabs exist per flavour and
per plan (`BIZ_TABS`, `PRO_TABS`), so a mistake there silently hides a paid
feature from the customer who paid for it.

### 6. ~~The Node cloud twin is half the size of the PHP one~~ — **withdrawn, the finding was wrong**
The first draft inferred from 2,284 lines of PHP versus 1,204 of Node that
"behaviour behind those routes may not match" and suggested closing, testing or
dropping the twin. Checking instead of inferring: **it is already tested, and
well.**

- The contract suite runs against a real PHP 8.3 + MySQL instance in CI (the
  `php-contract` job), not just against Node — same suite, same assertions.
- `route-parity.test.js` reads the routes out of both sources rather than a
  fixture, so adding an endpoint to one side is what fails it.
- It also asserts **every route is exercised by at least one contract test**, with
  an allowlist that requires a stated reason per entry.

The line-count gap is PHP verbosity — no framework, hand-rolled JSON and PDO —
not missing behaviour. Inferring a defect from a line count was the mistake.

One real limit, accepted rather than fixed: parity compares **path sets, not
(method, path) pairs**, so a path serving POST in one backend and not the other
would pass. The exposure is narrow, because any method a contract test drives is
run against both. Extending the extractor is not obviously worth it — this same
regex-over-two-languages extractor produced three rounds of false positives when
it was written, and a noisy guard is worse than a narrow one.

## Checked and found healthy

Recording these so they are not re-reviewed on a hunch later.

- **RTL** is in genuinely good shape: 64 `margin-inline` vs 4 `margin-right`,
  32 `inset-inline`, 25 `text-align: start`, plus 55 `[dir=rtl]` overrides and 2
  RTL tests. Logical properties dominate, which is what makes Arabic work.
- **XSS.** 429 `innerHTML` assignments looked alarming, so the highest-risk path
  was checked directly — customer-submitted text from the public intake form
  rendered in the owner's UI (`waiting-list.js`). Every DOM sink escapes; the
  five apparently-unescaped interpolations are plain-text message bodies, not
  HTML. Escaping discipline is real. What is missing is a *systematic* guard, not
  the escaping itself.
- **Dependencies.** `npm audit --omit=dev`: 0 vulnerabilities.
- **LAN API.** After the inventory projection, no endpoint dumps a raw store
  collection.
- **Cloud.** 73 tests pass; deployed build matches source.
- **iOS localisation.** en and ar both carry 117 keys — no drift.

## Features worth building, in order of evidence

The desktop has 17 tabs; the phone has 6. That gap is mostly correct — a shop
floor does not need a colour studio. But three desktop features are things people
do **away from the desk**, which is exactly what the phone is for:

1. **Quote on the spot** (`calculator`). A customer walks in holding a part. Today
   that means going back to the desktop. This is the strongest candidate: it is
   revenue, it happens standing up, and the calculator logic is already isolated
   in `lib/`.
2. **Log a failed print at the machine** (`waste`). Waste is recorded where it
   happens or it is not recorded at all — and unrecorded waste is exactly the
   number a shop most needs.
3. **Capture an expense with the camera** (`expenses`). A receipt is a photo; the
   phone is the camera. The companion already has `LabelCameraPicker`.

Beyond parity, the two that would matter most:

4. **Offline read cache** (see finding 3) — it makes every existing screen work
   in the places the phone is actually used.
5. **Tell the owner what changed while they were away.** The cloud already has
   web push and the desktop has an audit log; a daily "3 orders finished, 2 spools
   low" is a small amount of new code over parts that exist.

## Deliberately not recommended

- **Multi-shop / Phase 3 beyond the ODK.** The blocker is retired and the design
  is written; the remaining work is real but should wait for a shop that has
  asked for it. See [ORG-DATA-KEY](./KHAYT-3.0-ORG-DATA-KEY.md).
- **Shared inventory.** Same reason, and it is the only part needing more than
  last-write-wins.
- **Rewriting the theme system.** Nine shells is a lot of surface, but the
  reachability and contrast guards make it a maintained lot rather than a risky
  one.
